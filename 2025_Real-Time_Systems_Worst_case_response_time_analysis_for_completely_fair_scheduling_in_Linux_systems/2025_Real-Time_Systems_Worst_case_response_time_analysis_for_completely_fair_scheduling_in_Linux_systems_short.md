## 1. Introduction

* **組込みLinuxのリアルタイム需要**: 組込みシステム（ドローン、ロボットなど）におけるLinuxの普及に伴い、デッドラインやスループットなどのリアルタイム要件を満たす必要性が高まっている 。


* **従来のリアルタイムスケジューラの課題**: `SCHED_FIFO` などの絶対的な優先度に基づくリアルタイムスケジューラは、高優先度タスクを極端に優先するため、UIやカーネルタスクを含む低優先度タスクの応答性を著しく低下させ、システムを不安定にするリスクがある 。


* **計算集約型リアルタイム処理の台頭**: 近年、AI技術（3D物体検出など）の組込みCPU上での実行など、実行時間が長く重いリアルタイムタスクが増加しており、上記のような低優先度タスクへの悪影響がより顕著になっている 。


* **CFS活用のモチベーション**: デフォルトのスケジューラ（`SCHED_OTHER`）であるCFS（Completely Fair Scheduling）を利用すれば、CPU資源を公平に分配してシステム全体の応答性を維持しつつ、リアルタイムタスクを処理できる可能性がある 。


* **本研究の目的**: CFSは実行中に動的にタイムスライスやタスク優先度を変化させるため、従来の最悪ケース応答時間（WCRT）分析手法が適用できなかった 。本論文は、CFS下における**世界初のWCRT分析手法**を提案し、開発者がスケジューラを適切に選択できるようにする 。

## 2. Background and related work

### 2.1 Linux in embedded systems

* **Linuxの利点と採用**: オープンソース、適応性、堅牢性といった利点から、ネットワーク機器、自動車、ロボット、宇宙船制御など多岐にわたる組込み分野でLinuxが標準的に採用されている 。


* **デフォルトスケジューラ（CFS）**: カーネルバージョン 2.6.23 から 6.5 までCFSがデフォルトとして使用されてきた 。最新カーネル 6.6 ではEEVDFが導入されたが、産業界では長期間検証された安定カーネル（CFS搭載）が好まれるため、今後もCFSの利用は長く続くと予想される 。


* **リアルタイムサポート**: Linuxカーネルは `SCHED_RR`, `SCHED_FIFO`, `SCHED_DEADLINE` といったリアルタイムスケジューラをネイティブでサポートしており、さらに `PREEMPT_RT` パッチを適用することで、カーネルコードを完全プリエンプティブルにして determinism（決定論性）を高めることができる 。



### 2.2 Worst case response time analysis

* **WCRTの定義**: タスクがリリースされてから実行を完了するまでの最長時間を指す 。


* **固定優先度（FP）分析との違い**: 従来のFPプリエンプティブスケジュールにおけるWCRT計算式は、高優先度タスクによる干渉のみを累積するが、優先度やタイムスライスが動的に変化するCFSには直接適用できない 。


* **他のフェアシェア分析との違い**: DRRやWRR、LRRといった公平分配アルゴリズムを対象とした既存のWCRT分析は、固定的なラウンドや処理ウィンドウに基づいており、実行可能タスクの総重みに応じて動的にタイムスライスを変更し、タスクの実行順序がランタイムで入れ替わるCFSのOperationalなメカニズムとは根本的に異なるため適用できない 。


* **優先度割り当て手法（OPA）との非互換性**: リアルタイム研究で広く使われるOPA（Optimal Priority Assignment）は「自身のWCRTが低優先度タスクの相対的な順序に依存しない」等の前提条件を要するが、CFSでは全タスクが互いの重みに比例して干渉し合うためOPAの条件に違反し、互換性がない 。

## 3. Problem definition and system modeling

* **タスクモデル**:
    * タスクセット $\mathcal{T}$ は、独立した周期的（periodic）または散発的（sporadic）なリアルタイムタスクから構成される 。


    * 各タスク $\tau_i$ は、最悪ケース実行時間（WCET） $C_i$、重み $w_i$、相対デッドライン $D_i$、周期または最小インターアライバル時間 $T_i$ を持つ 。


    * 時間は離散時間モデルを採用し、重みは正の整数とする（ $\{C_i, w_i, D_i, T_i \in \mathbb{Z}_{>0}\}$ ） 。相対デッドラインは周期以下（ $D_i \le T_i$ ）と仮定し、タスクの初期リリースオフセットは未知とする 。




* **システムモデル**:
    * 単一のCPU（シングルコア）環境を前提とする 。


    * プロセッサ以外の共有リソースはなく、タスクは自己サスペンド（self-suspend）しない 。


    * コンテキストスイッチやスケジューリングのオーバーヘッドは無視できるものとし、特別なタスクグループ化機能（group scheduling）は使用しないデフォルトのLinux設定を想定する 。




* **スケジュール可能性の定義**:
    * 分析によって導出される $\tau_i$ の保守的な推定WCRTを $\tilde{R}_i$ と表現する 。


    * 条件 $\tilde{R}_i \le D_i$ を満たせばそのタスクはスケジュール可能（schedulable）と判定され、すべてのタスクが満たせばタスクセット全体がスケジュール可能と見なされる 。

## 4. Completely fair scheduling

* **CFSの基本思想**: 理想的なマルチタスクハードウェア（全タスクにCPUを均等に同時分配する）を単一プロセッサ上で擬似的にモデル化し、実行可能タスク間でCPU時間を公平に切り分けるアルゴリズムである 。


* **vruntime (仮想実行時間)**:
    * CFSは各タスクが消費したCPU時間を追跡するため、`vruntime` という指標を使用する 。


    * 実行可能（runnable）なタスクは `vruntime` をキーとして赤黒木（Red-Black tree）構造のランキューにソートされ、CFSは常に最も `vruntime` が小さいタスクを次に実行するタスクとして選択する 。


    * タスクがCPUを使用すると、その割り当てられた重み $w_i$ に反比例する形で `vruntime` が累積・更新される（ $V_i^t = V_i^{t'} + \Delta_i \cdot \frac{w_0}{w_i}$ ） 。




* **minimum vruntime**:
    * システムはランキュー内の最小の `vruntime` を追跡し、`minimum vruntime` ( $V_{min}^t$ ) という基準値を単調増加させることで、タスク間の `vruntime` のレベルを一定に保つ 。




* **Nice値と重み**:
    * ユーザー空間の優先度（Nice値: -20 〜 +19）はカーネル内部で重みにマッピングされる 。Nice値0の基準重み $w_0$ は1024であり、Nice値が1下がる（優先度が上がる）ごとに重みは約1.25倍に増加する 。




* **動的タイムスライス**:
    * 固定のクォンタム（時間幅）を使用する他のスケジューラとは異なり、CFSはターゲットレイテンシ $L$ と最小グラニュラリティ $G$、およびその瞬間の実行可能タスクの総重みに対する自身の重みの比率からタイムスライス $\delta_i^t$ を動的に決定する 。


    * 実際のプリエンプションは、タイマー割込みの間隔（jiffy、 $\mathcal{J}$ ）の倍数単位に補正されたタイムスライス $\sigma(\delta_i^t)$ に基づいて発生する 。




*  place_entity による独占防止:
    * 長時間スリープしていたタスクが起床（リリース）した際、その `vruntime` が著しく低いためにCPUを独占してしまう現象を防ぐため、起床時の `vruntime` を最低でも $V_{min}^t - L/2$ に引き上げる制限が課される 。

## 5. Proposed technique

### 5.1 Worst case response time analysis

* **分析アプローチ**: 動的にタイムスライスが変化するCFSでは、最悪ケースの到着パターン（クリティカルインスタンス）を特定することが困難である 。そこで本研究では到着パターンの特定を避け、CFSが持つ「実行可能タスク間の `vruntime` の差（分散）に上限がある」という性質を応用する手法をとった 。


* **vruntime分散に基づく干渉量の上限算出**:
    * **Lemma 1**: ターゲットタスク $\tau_i$ の実行中に他タスク $\tau_j$ から受ける干渉量 $\mathcal{I}(\tau_j \rightarrow \tau_i, R_i)$ は、 $\tau_i$ のリリースから完了までの間の $\tau_j$ の `vruntime` の増加量（重み比でスケーリングしたもの）によって安全に上限付けられる 。


    * **Lemma 2 & 3 / Corollary 1**: CFSの公平性維持機能から、 $\tau_i$ がリリースされた瞬間（時間0）における $\tau_j$ と $\tau_i$ の `vruntime` の初期差の下限（ $V_j^0 \ge V_i^0 - \alpha_i - L/2$ ）を証明・導出する 。


    * **Lemma 4**: $\tau_i$ が実行を完了する瞬間（時間 $R_i$ ）における $\tau_j$ の最大 `vruntime` の上限（ $V_j^{R_i} < V_i^0 + C_i \cdot \frac{w_0}{w_i} + \gamma_{i,j}$ ）を導出する 。


    * **Lemma 5**: これらを統合し、初期状態と終了状態の `vruntime` 変動限界の差分を取ることで、 `vruntime` の分散に依存した干渉量の上限式（式28）を導く 。




* **総ワークロードによる上限のタイト化（洗練）**:
    * `vruntime` の分散による上限だけでは、他タスクのWCET $C_j$ が $C_i$ に比べて極端に小さい場合、実際には発生し得ない過剰な干渉量が計算され、過度な悲観論（Pessimism）が生じる 。


    * これを解消するため、プロセッサが休止せず連続してビジー状態になる最大期間（Maximum busy period）の長さ $\mathcal{L}_i$ を反復式（式33）によって求める 。


    * **Lemma 6 / Corollary 2**: 期間内にリリースされ得る最大のジョブ数 $\tilde{N}_j(R_i)$ から総ワークロードの絶対的な上限 $\tilde{W}_j(R_i)$ を算出し、 `vruntime` 分散の上限式との小さい方（ `min` ）を取ることで、干渉量の上限 $\tilde{\mathcal{I}}$ をタイトに絞り込む 。




* **WCRT分析アルゴリズム（Algorithm 1）**:
    * 初期値を $\tilde{R}_i = C_i$ とし、他タスクからの最大干渉量を累積しながら応答時間を反復計算によって更新する 。


    * 値が前回のループと一致して収束（固定点に到達）するか、デッドライン $D_i$ を超過するまで繰り返す 。


    * このアルゴリズムは必ず有限回数で終了し（Theorem 2）、計算複雑性は $\mathcal{O}(n^2 \cdot D_{max})$ となる 。





### 5.2 Nice value assignment

* CFSでは各タスクに設定されたNice値（重み）のバランスがシステム全体のスケジュール可能性を決定するため、適切な優先度割り当てを行う2つのアルゴリズムを提案した 。



#### 5.2.1 Deadline-aware heuristic algorithm

* デッドラインの緊急度が高いタスク（ $D_i$ が短いタスク）に対して、より高い優先度（大きな重み）を自動的に割り当てるヒューリスティック手法 。


* 各タスクのデッドラインと最大デッドライン $D_{max}$ との比率を対数スケール（ $ln(D_i/D_{max})$ ）で圧縮することで、短いデッドライン間の微小な差を強調しつつ、長いデッドライン間の差のインパクトを抑制する 。


* Algorithm 2に従い、デッドライン比の影響度を制御するパラメータ $\lambda$ を最小値から徐々に増やしていき、提案のWCRT分析手法（Algorithm 1）をパスする最小の $\lambda$ を探索する 。これにより、リアルタイム性能を担保しつつ不要な優先度差を抑え、低優先度タスクの公平性と全体的な応答性を最大化できる 。



#### 5.2.2 Genetic algorithm

* タスク数 $n$ に対して $40^n$ という膨大な探索空間となるNice値の組み合わせに対処するためのメタヒューリスティック手法 。


* 各タスクのNice値を「遺伝子（gene）」、その並び（割り当て案）を「染色体（chromosome）」として定義する 。


* 適合度関数（fitness）は、提案のWCRT分析手法をベースに改造し、そのNice値の組み合わせによって「スケジュール可能（デッドラインを遵守可能）となった個別のタスク数」をカウントしてスコアとする 。


* ルーレットホイール方式による選択、一点交叉、突然変異（確率5%）、および親染色体との置換のステップを繰り返し、全タスクがスケジュール可能になるか、タイムアウト（5秒）に達するまで集団を進化・最適化させる 。

## 6. Experiment

### 6.1 Experimental setup

#### 6.1.1 Taskset

* **合成タスクセット**: 組込みAIなどの長時間処理タスクをモデル化し、UUniFastアルゴリズムを用いて周期・デッドラインが30ミリ秒〜3秒の範囲に収まるタスクをランダム生成（タスク数4〜20、総利用率0.2〜0.8、各構成100セット） 。


* **実世界のタスクセット**: Thales Alenia Space（TAS）が提供する衛星オンボードソフトウェアのデータに基づき、21個の周期的タスク（ハードリアルタイム18個、ソフトリアルタイム3個、総CPU利用率約74%）からなるデータセットを構築 。



#### 6.1.2 CFS simulator

* 初期リリースオフセットがランダムに変動する中での最悪ケースを網羅的かつ効率的に探索するため、Java 11でイベント駆動型のカスタムCFSシミュレータを実装 。最大1000個の異なる実行パスを生成して最悪の応答時間を計測し、実機挙動との比較・可視化によりシミュレータの正確性を検証済み 。



#### 6.1.3 Implementation

* **実機環境**: DebianベースのRaspberry Pi OS（Linuxカーネル 5.15.92）を搭載した Raspberry Pi 4（Cortex-A72 CPU）を使用 。カーネルパラメータは $L=18\text{ ms}$, $G=2.25\text{ ms}$, $\mathcal{J}=1\text{ ms}$ とした 。


* **計測方法**: C言語と `pthread` ライブラリを用いてタスクを実装し、各スレッドで指定時間 $C_i$ のビジーウェイトを実行 。実機測定後に `clock_gettime()` で得られた正確な実測WCETを抽出し、これをシミュレータや提案の分析手法の入力にフィードバックすることで公平な比較を行った 。



### 6.2 Evaluation on nice value assignment

* 全タスクに同じNice値を割り当てる「Baseline」、提案の「Heuristic（Algorithm 2）」、提案の「GA（Algorithm 3）」の3戦略で、スケジュール可能と判定されたタスクセット数を比較（表2） 。


* **結果**: Baselineでは高負荷時にほぼすべてスケジュール不可能となったが、HeuristicおよびGAは成功数を劇的に向上させ、割り当てアルゴリズムの有効性が証明された 。GAはHeuristicより高い成功率を達成する一方、計算時間が増大するトレードオフ（Heuristic：2〜50 ms、GA：37〜5112 ms）が確認された（図5） 。



### 6.3 Evaluation on WCRT analysis

* 2000個の合成タスクセットを用い、提案の分析手法（予測）が実機やシミュレータの最悪応答時間（実測）を正しく包絡できているかを評価 。


* **実機との比較（表3）**: 平均予測精度（Accuracy）は**約89%** 。タスク数や利用率が増すと精度が下がる傾向があるが、これは各タスクの最悪干渉が現実の短い実行（5回）の間に同時発生しにくいためであり、分析手法が保守的に機能していることの裏返しである 。


* **シミュレータとの比較（表4）**: 平均予測精度は約98%に到達 。シミュレータが最大1000通りの実行パスを効率的に探索して真の最悪ケースに肉薄したため、FN（実際はデッドラインに間に合うが分析で不合格とする過剰 overestimated ケース）が大幅に減少した 。


* **保守性の実証**: すべての実験ケースにおいて、**False Positive（実際はデッドラインをミスするが、分析で合格と誤判定する危険なケース）は 0** であった 。これにより、提案手法がリアルタイムシステム検証において完全に安全（保守的）であることが実証された 。



### 6.4 Evaluation on CFS

#### 6.4.1 Comparison with RT schedulers

* TASの衛星ソフトウェアタスクセットを実行し、CFSとリアルタイムスケジューラ（`SCHED_FIFO`, `SCHED_RR`, `SCHED_DEADLINE`）の実機応答時間を比較（表5、図6） 。


* **結果**: 優先度の高い一部のタスクの応答時間はリアルタイムスケジューラが勝るものの、CFSはプロセッサをより公平に分配するため、システム全体のタスクの平均応答性を一様に高めることができた 。


* **短いタスクの逆転現象**: WCETがCFSの最小グラニュラリティ（2.25 ms）よりも短いタスク群において、CFS下では1回のタイムスライスで実行が完了するため、リアルタイムスケジューラ下よりも平均応答時間が劇的に短縮される現象が確認された 。さらに、本実験の構成ではCFSを用いてもすべてのハードリアルタイムタスクがデッドラインを完全に遵守できた 。



#### 6.4.2 Suitability of CFS

* **CFSが不得意なケース**: 遅延を明示的に制御する機構を持たない性質上、タスク数が極めて多い、総CPU利用率が限界に近い、あるいはタスク周期が非常に短い（10ミリ秒未満など）ケースでは、デッドラインまでの許容マージンが狭く、CFSではスケジュールが失敗しやすいことがデータから示された（表6） 。


* **CFSが適したケース**: 反対に、近年のAI駆動型リアルタイム処理のように「計算負荷が非常に高く、実行時間や周期が数百ミリ秒〜数秒単位と長め」のタスク特性においては、CFSはリアルタイムスケジューラの有力な代替選択肢となる 。リアルタイム性能を満たしつつ、通常のUIタスクやカーネルタスクの応答性を維持してシステム全体のバランスを最適化できる 。

## 7. Conclusion

* **研究の成果**: 本論文は、Linuxのデフォルトスケジューラ（CFS）を対象とした**世界初の最悪ケース応答時間（WCRT）分析手法**を確立し、その理論的正当性と完全な保守性（安全設計）をシミュレータおよび実機実験によって強固に証明した 。


* **実用性**: デッドライン認識型のNice値（優先度）最適化手法を同時に提供したことで、過酷なリアルタイム制約下でもCFSを安全に設計 space exploration やシステム検証に組み込むことが可能となった 。


* **今後の展望**:
* Partitioned scheduling をベースとしたマルチコアシステムへの拡張、共有リソース競合（Contention）やタスク依存関係のサポート 。


* Linuxカーネル 6.6 以降に新しく採用されたデフォルトスケジューラ **EEVDF** への本アプローチ（vruntimeの分散・変動バウンド解析）の移植・適用 。EEVDFは遅延を明示考慮する性質上、CFSが苦手とした latency-sensitive なショート周期タスクでもより優れたスケジュール可能性を提供できると期待されている 。
